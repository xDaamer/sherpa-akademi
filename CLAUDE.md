# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

akademITU — a Turkish-language marketing site (YKS/LGS exam coaching) built as a single-page React app with a small Express backend (`server.ts`). The backend proxies the two-step lead-capture form into Supabase; that proxy was unreachable in production on Vercel for a long time (root cause found and fixed 2026-09-08 — see Architecture below) and the form had meanwhile been rewired to talk to Supabase straight from the browser. On 2026-09-09 everything moved back behind the proxy and the browser stopped touching Supabase entirely; there is now also a user portal with cookie-based auth. On 2026-09-10 that portal moved onto its own subdomain: **login stays at `akademitu.com/login`, the panel itself lives at the root of `portal.akademitu.com`** (same Vercel project, second domain — see Architecture). It originated from a Google AI Studio scaffold (see `metadata.json` / `.env.example` Gemini references) but the app does **not** currently call the Gemini API anywhere in `src/` or `server.ts` — treat those as inherited boilerplate, not live functionality.

## How this project is verified — read before testing anything

**The local `.env` is deliberately incomplete and always will be.** It holds `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `ALLOWED_ORIGINS`, but **never `SUPABASE_SERVICE_ROLE_KEY`**. Do not ask for it, do not add it, and do not work around its absence.

The consequence is larger than it looks: the service role backs lead capture, testimonials, the rate limiter, the audit log, the phone→email lookup **that login itself depends on**, and all of `/api/admin/*`. So on localhost **you cannot log in at all**, and anything behind a session is unreachable. `npm run dev` is still useful — it verifies validation, origin checks, 401/403 wiring and that the server boots — but it can never confirm a feature works.

**Therefore: push to `main` and verify against the live deployment.** That is the normal, expected workflow here, not a last resort — `main` auto-deploys to Vercel (~35 s) across `akademitu.com`, `www` and `portal.akademitu.com`, and production has the full environment. Pushing for the purpose of testing needs no separate permission; it is how this repo is tested.

Before pushing: `npm run lint` and `npm run build` must pass, and if anything in `server.ts`'s import graph changed, re-run the ESM cold-start probe (see the Vercel note in Architecture). Also check `git log origin/main..HEAD`: a push takes every unpushed commit with it, and any commit that ships a `supabase-*.sql` needs that SQL run in the SQL Editor **first** (this includes `supabase-teacher-contract.sql`) — on 2026-10-09 an unrelated push carried the availability commit out before its migration and the panels' lesson queries failed until it was applied. After pushing: wait for `READY`, then exercise the real endpoints over HTTPS. `npm run test:panels` is written for exactly this and takes `--base https://www.akademitu.com --admin 05xx:pw`.

When a live check writes data (a lead, a test account), say so, and clean it up afterwards unless it was asked for. A previous deployment stays available as a Vercel rollback candidate if a push turns out to be wrong.

## Commands

- `npm run dev` — starts `dev-server.ts` via `tsx`, which boots Express (imported from `server.ts`) with Vite in middleware mode (one process serves both the API and the SPA with HMR). **Login does not work here** — see the verification section above. Not `server.ts` directly — see the vite-isolation note below.
- `npm run build` — `prebuild` runs `scripts/blog/check.ts`, `scripts/generate-seo.ts` (writes `public/sitemap.xml` / `public/robots.txt` from `need.json`) and `scripts/generate-images.ts`; then `vite build`, then **`vite build --ssr src/entry-server.tsx --outDir dist-ssr`**, then bundles `server.ts` to `server-dist/server.cjs` with esbuild; then `postbuild` runs **`scripts/prerender.ts`** followed by `scripts/blog/build.ts`. The order is load-bearing in both directions — prerender needs the client build's `dist/index.html` as its shell and the SSR bundle to render from, and it must run before the blog builder, which owns turning `dist/sitemap.xml` into a sitemap index.
- `npm start` — runs the built `server-dist/server.cjs` (production mode, serves static `dist/` and falls back to `index.html` for SPA routes).
- `npm run lint` — `tsc --noEmit`. There is no separate lint tool (no ESLint) and no general test suite/framework in this repo — don't assume `npm test` exists.
- `npm run test:panels -- --base https://www.akademitu.com --admin 05xx:pw` — the **only** executable test in the repo, and it runs against the **live deployment** (see the verification section above; it cannot work on localhost). Only the admin credential is needed: the script opens its own teacher and student accounts through the panel, has the teacher accept the contract when one is published (after asserting that the gate blocks the panel first; this writes an acceptance row that cannot be deleted without the SQL escape hatch, i.e. disabling the append-only trigger), checks the teacher-availability rules, assigns a lesson from the teacher's program (plus a 25-min trial lesson it deletes again), records a fee, marks the lesson taught, comments on it, checks that the student sees all three, lists the form leads (read-only — it writes no lead), then asserts every cross-role 403 and deletes the lesson and payment it made. It does not delete the accounts — the panel has no account deletion — and prints them at the end. It deliberately does **not** cover RLS: that lives in `supabase-teacher-panel-tests.sql`, run in the Supabase SQL editor inside `BEGIN ... ROLLBACK`. Both must pass; they test different layers and either alone is misleading.
- `npm run clean` — removes `dist/`.
- `npm run push` — plain `git push`, nothing more (a bare alias; `git push` works the same).

**Versioning is manual, by design.** `need.json`'s `site.version` is the source of truth (the footer renders it). Bump it by hand when you want a new version to show. There used to be `scripts/push.cjs` and `scripts/version-bump-on-push.cjs` that auto-bumped the patch on every push; both were deleted on 2026-09-08 because nothing called them any more — `package.json`'s `push` script had become a plain `git push` and `.husky/pre-push` was disabled, so this file was documenting behaviour that hadn't existed for a while. Don't reintroduce automatic bumping without wiring it somewhere real.

## Architecture

**Single Express app (`server.ts`), split entry points.** `server.ts` defines and exports the Express `app` (routes, middleware) and is imported by two different entry points — it never imports `vite` itself and never binds a port on its own:
- Dev: `dev-server.ts` imports `app` from `server.ts`, adds Vite in middleware mode (`app.use(vite.middlewares)`), and calls `app.listen()`. `vite` is a dev-only dependency deliberately kept out of `server.ts`'s own import graph — a static or dynamic `import ... from "vite"` there gets traced into the Vercel serverless function bundle (see below) and was confirmed to break it at runtime (`FUNCTION_INVOCATION_FAILED` on every request, even a plain `GET /api/health`).
- Prod (`npm start`, not Vercel): `server.ts`'s own `startProductionServer()` (guarded by `!process.env.VERCEL && NODE_ENV === "production"`) serves the static `dist/` output and sends `index.html` for all non-API routes (SPA fallback).
- Vercel: `api/[...path].ts` imports `app` from `server.ts` and wraps it as a serverless function; `vercel.json`'s rewrite (`/((?!api/).*) -> /index.html`) explicitly excludes `/api` so a broken function fails as a 404 instead of silently being served `index.html` (which is what turns into a confusing 405 on non-GET methods). **The long-standing `FUNCTION_INVOCATION_FAILED` on every `/api/*` request was diagnosed and fixed on 2026-09-08.** Vercel's runtime log gave the actual cause:

```
ERR_MODULE_NOT_FOUND: Cannot find module '/var/task/server'
imported from /var/task/api/[...path].js
```

`api/[...path].ts` imported `"../server"` **without a file extension**. Because `package.json` sets `"type": "module"`, the compiled function runs as ESM, and Node's ESM resolver — unlike CommonJS — does not guess extensions. Every request died at cold start before reaching any route, which is why even `GET /api/health` 500'd. The fix is the `.js` extension (`import app from "../server.js"`); `dev-server.ts` was aligned to the same form so the mistake can't reappear unnoticed. Note this is unrelated to the `vite`-in-the-import-graph trap described above, which is a separate, still-valid constraint.

A second, independent bug surfaced while verifying that fix: `server.ts` reads `need.json` via `readFileSync(process.cwd() + "/need.json")`, and Vercel's file tracer only follows **static imports** — it cannot see a runtime path, so `need.json` was never packaged and `/api/config` returned an empty object. `vercel.json` now declares it explicitly:

```json
"functions": { "api/**": { "includeFiles": "need.json" } }
```

Both fixes are verified locally (esbuild → ESM → invoke handler reproduces the original error before the change and returns 200 after) but **not yet confirmed on a live deployment**. This matters much more than it used to: since 2026-09-09 the lead form, testimonials and the whole portal go through this function, so if it breaks, they all break. Re-run that local ESM probe after touching anything in `server.ts`'s import graph.

**The marketing pages are prerendered to static HTML (added 2026-09-15).** Until then the server returned the same empty shell for every route — measured on production: `curl https://www.akademitu.com/` gave 6391 bytes containing `<div id="root"></div>` and **0 `<h1>`, 0 `<h2>`, 0 `<a href>`, 0 JSON-LD**, with the homepage's `<title>`, description and canonical on every path. All of that markup existed in the React source; it was just client-rendered or injected in `useEffect`, so any crawler that does not run JS saw nothing. `seo-audit/faz-5-taranabilirlik.md` had this on file as K-01.

`scripts/prerender.ts` (postbuild) imports the SSR bundle and writes five files: `dist/index.html` (`/`), `dist/gizlilik-politikasi/index.html`, `dist/kullanim-kosullari/index.html`, `dist/404.html` and `dist/app.html`. It reuses the blog generator's mechanism exactly — **Vercel checks the filesystem before applying rewrites**, so a real file at a path beats the SPA catch-all and no rewrite rule is needed for the three marketing routes. Per-route `<head>` is rewritten from the same `need.json` `seo.pages` array that `PageMeta`'s `seoPage()` reads, so the two cannot drift.

Three things about it are easy to break:

1. **`motion`'s `initial` styles serialize into the server output.** Without a guard the packages grid — the prices — lands in the static HTML as `style="opacity:0"`: the page looks full and the crawler sees nothing, which is the silent version of the bug this whole change fixes. `src/lib/ssr.ts` exports `IS_SERVER` and the five call sites use `initial={IS_SERVER ? false : {…}}`. `prerender.ts` asserts the output contains no `opacity:0` and **fails the build** if it does.
2. **JSON-LD had to move out of `useEffect` and into JSX** (`App.tsx`, `FAQSection.tsx`, `PackagesSection.tsx`), since effects never run during server render. The pattern was already in the repo — `LegalPageChrome.tsx` renders `BreadcrumbList` this way. It also deleted a real bug: `FAQSection`'s effect depended on `[faqs]`, a fresh array each render, so every accordion click appended another script to `<head>`.
3. **`main.tsx` stays on `createRoot`; do not switch to `hydrateRoot`.** The server always renders in `'main'` mode (`host.ts` returns it when `window` is undefined), but on localhost and every `*.vercel.app` preview the client's `routingMode()` returns `'both'` and mounts a materially different route tree — a guaranteed hydration mismatch on every preview deploy. The reasoning is spelled out above the call.

**`vercel.json`'s rewrites had to grow with it, and the order is what makes it correct.** `dist/index.html` is no longer an empty shell, so it can no longer be served to everything: the portal host and `/login` now rewrite to `/app.html` (the empty shell). **There is deliberately no final catch-all rewrite** (removed 2026-10-18): an unmatched path falls through to Vercel's own handling, which serves `dist/404.html` with a real **404 status**. A rewrite to `/404.html` used to sit there and returned it with **200** — every unknown URL (`/llms.txt`, `/Blog`, `/manifest.json`) was a soft 404. `404.html` still carries `noindex, follow` and no canonical, without JS having to run. Do not add the catch-all back.

**But a rewrite cannot reach the portal host's root, and that is worth understanding before touching any of this.** Vercel's order is redirects → **filesystem** → rewrites. `/` resolves to `index.html` on disk, so no rewrite ever runs for it — measured on production, where `portal.akademitu.com/` served the full marketing homepage despite the host rule. This is the *same* mechanism that makes prerendering work at all (`/gizlilik-politikasi` is a real file, so it never reaches the catch-all), and it cuts both ways. The host rule still does its job for portal paths that have no file (`/ogretmen`, `/yorumlar`, `/yonetim`); only the root is beyond its reach. The only infrastructure-level fix is middleware, the one thing that runs before the filesystem — rejected here because the whole point of this design is that no function runs for a page, and this repo has already paid for serverless fragility once (the `FUNCTION_INVOCATION_FAILED` saga above). Instead `prerender.ts`'s `panelHostKorumasi()` injects six lines into `dist/index.html` only: a `<head>` script that stamps `data-panel-host` when the hostname's first label is `portal` (the same test `routingMode()` uses), a style that hides `#root` while that attribute is present, and a script at the end of `<body>` that empties `#root` and removes the attribute — so nothing paints and React mounts into a clean, visible container. On every other host the attribute is never set and the rule never matches. The problem it solves is cosmetic (the panel always worked; `noindex` headers were never affected), and so is the fix. That closes faz-5's soft-404 finding for the portal root (which is still 200, since it is a real file); unknown paths on the main host now return a real 404, see above. Note `vercel.json` is schema-validated and **rejects unknown top-level keys** — a `_note` field there failed a deploy before the build even started, and the file takes no comments either, which is why the rewrite reasoning lives in `scripts/prerender.ts`'s header.

Two gaps in the prerendered HTML are deliberate and documented there: `TestimonialsSection` fetches in `useEffect`, so its `<h2>` is absent, and only the open FAQ answer is in the DOM (the FAQPage schema carries all six).

**Two hosts, one deployment (changed 2026-09-10).** The site is served from two hostnames out of **the same Vercel project and the same `dist/` build**:

| host | what it serves |
| --- | --- |
| `akademitu.com` / `www.akademitu.com` | marketing pages + the login screen at `/login` |
| `portal.akademitu.com` | the panel, at the **root** (`/`) |

`portal.akademitu.com` is a **subdomain**, not a second registered domain, and that is load-bearing rather than cosmetic — see the cookie note below. Adding it is a DNS `CNAME` plus a Domains entry in the Vercel project; no separate build, no second repo, no separate env vars.

**Which pages exist is decided by HOST, not by path** (`src/lib/host.ts` — the single place that reads `window.location`; no component should read the hostname itself). `routingMode()` returns:
- `'portal'` — panel only (`/` is the dashboard).
- `'main'` — marketing + `/login` only.
- `'both'` — **localhost and `*.vercel.app` previews**, where both trees mount and the panel sits at `/panel`. This exists because a single-host environment otherwise has nowhere to put the panel; `npm run dev` would not be able to open it at all. It is not a leak: **hiding the panel's JS was never the security boundary** — the boundary is the session cookie plus RLS, and the bundle is shared by both hosts anyway.

`VITE_MAIN_ORIGIN` / `VITE_PORTAL_ORIGIN` override the two live addresses so the split can be reproduced locally against `/etc/hosts` entries (see `.env.example`); `vite.config.ts` derives `server.allowedHosts` from exactly those two values, so Vite's host check and the app's own idea of its address cannot drift apart.

Cross-host navigation cannot use react-router — `<Navigate to="https://...">` is treated as a relative path. `src/components/CrossHostRedirect.tsx` picks `window.location.replace` for absolute targets and `<Navigate>` for relative ones, so the same JSX is correct in all three modes.

**The session cookie carries `Domain=.akademitu.com` — this is what makes the split work at all** (`server/cookies.ts`). Cookies default to *host-only*: without the `Domain` attribute, a user logging in at `akademitu.com/login` would land on `portal.akademitu.com` and be treated as logged out. Because both hosts sit under one registered domain, the guide's "handoff token" pattern is unnecessary — **no token is ever put in a URL**, so none can leak through access logs or `Referer`. `sameSite=lax` still suffices, because SameSite is evaluated on the registered domain (eTLD+1), not the host, so the two are "same-site" to the browser.

Two consequences that are easy to get wrong:
1. **`clearSessionCookies` must pass the same `domain`.** A browser only deletes a cookie when name + path + domain match exactly; a domain-less delete silently leaves the `.akademitu.com` cookie in place and "logout" does nothing.
2. **Legacy host-only cookies shadow the new ones.** A `Domain=` cookie does *not* overwrite a same-named host-only cookie — the browser keeps both and sends both (`ak_at=old; ak_at=new`), and `cookie-parser` takes whichever comes first. `setSessionCookies` therefore expires the host-only variants in the same response. Those lines look redundant and are not: they are needed for every visitor who logged in before 2026-09-10.

The `Domain` value is **derived from the request host**, not hardcoded, because a fixed `.akademitu.com` would break `localhost` and `*.vercel.app` previews — a browser silently drops a cookie whose `Domain` does not cover the request's host, which fails as "login appears to succeed, session never exists". `COOKIE_DOMAIN` overrides the derivation.

**The cost of the shared cookie is subdomain takeover.** Any host under `.akademitu.com` can now read *and write* the session cookie. A dangling DNS record or an untrusted service parked on a subdomain is now a portal compromise. `__Host-` would close this but is by definition incompatible with `Domain`; this is the unavoidable trade of a two-host setup. A double-submit CSRF token would *not* help here either (an attacker who can read the cookie can read the token) — see the reasoning in `server/security.ts`.

**Edge-level routing lives in `vercel.json`'s `redirects`, keyed on `host`.** The old `/portal` and `/portal/panel` addresses were live for a while and may sit in bookmarks; they 308 to `/login` and `https://portal.akademitu.com/`. The same redirects also exist as React routes — the `vercel.json` ones fire before any JS runs (and are what search engines see), the React ones cover local/preview and in-app navigation. Host values are **anchored regexes** (`^portal\.akademitu\.com$`); leaving them unanchored would make the main-host rules match the portal host as a substring.

**`need.json` is the single source of site config.** Domain, contact info, social links, and the SEO page list all live in `need.json` and are consumed in three places that must stay in sync conceptually: `scripts/generate-seo.ts` (pre-build generation of `public/sitemap.xml` + `public/robots.txt`, run via the `prebuild` hook), `vite.config.ts` (replaces the `{{site.title}}`-style placeholders that `index.html` actually uses), and `server.ts` (`/api/config` only). `server.ts` used to serve its own dynamic `/sitemap.xml` and `/robots.txt`; those routes were dead duplicates of the static files (and shadowed them in dev, producing different output than production) and were removed on 2026-09-08. When the real production domain/contact details change, edit `need.json`, not the individual files (README calls this out explicitly).

**All Supabase traffic goes through `/api/*` — the browser never talks to Supabase (changed 2026-09-09).** `src/lib/supabaseClient.ts` is **deleted** and `VITE_SUPABASE_*` no longer exist; there is no Supabase key or URL in the client bundle (removing the client library also cut the main chunk from 683 kB to 468 kB). The single HTTP entry point is `src/lib/api.ts` (`apiFetch`, `credentials: 'include'`).

Be precise about *why* this was done, because the obvious reason is wrong: **Supabase's anon key is public by design** — it is a signed JWT carrying only "which project, which role", and hiding it buys nothing on its own. The real gains are:
1. `anon` now has **zero privileges on every table** (`supabase-portal-auth.sql`). That is the actual security boundary, and it is only possible because nothing in the browser needs the key any more.
2. Session tokens live in `httpOnly` cookies (`server/cookies.ts`). Supabase's browser client stores them in `localStorage`, where any XSS can read them. With a portal this stopped being theoretical.
3. Per-IP rate limiting became possible (`public.auth_attempts`). This was explicitly impossible at the RLS/PostgREST level, which is why the old design fell back to a blunt site-wide 20/minute trigger.

**Server-side Supabase clients — which one you use IS the security model** (`server/supabase.ts`):
- `anonServerClient()` — auth calls only (login/signup/refresh). Holds the anon key, which now lives solely on the server.
- `userClient(accessToken)` — **all logged-in user data**. Built per request from the cookie's JWT, so RLS applies as that user. An authorization bug in a route still hits the RLS safety net.
- `serviceClient()` — **bypasses RLS.** For things that belong to nobody: lead capture (nobody is logged in yet), published testimonials, the rate-limit counter, and the phone→email lookup at login (the one moment when no session can exist yet). Reading user data with this defeats the entire layer — with one deliberate exception, `/api/admin/*`, where the admin's legitimate scope is every row and account creation needs the Admin API anyway; the reasoning and what it costs are in the admin section below and at the top of `server/routes/admin.ts`.

**Login has a second route: username** (added 2026-09-11). `profiles.username` is optional, lowercase, 3–30 of `[a-z0-9._-]`, unique among non-NULL values, and **`@` is forbidden** — the point is that it can never be mistaken for an email. `auth.users.email` still exists because Supabase Auth requires it, but it is derived from the phone and never shown or typed. The login screen defaults to phone (every account has one; usernames are opt-in) and offers "Kullanıcı adı ile giriş yap" under the contact line; switching clears both fields, since one identifier is not a draft of the other. Values are lowercased on the way in, so `Ahmet` and `ahmet` are the same account and the unique index resolves the lookup directly. `auth_attempts` gained a `username` column rather than reusing `phone`: the report answers "which account was attempted", and writing a username into a column called `phone` would make it lie.

**Auth: login by phone, and there is no signup.** Accounts are created by hand — there is no registration screen and **no `/api/auth/signup` endpoint**. Removing the form while leaving the endpoint would have protected nothing (anyone could POST to it), so both are gone; `supabase-portal-auth.sql` §1b documents the two-step manual procedure (Dashboard "Add user" with *Auto Confirm User* ticked, then one `INSERT` into `profiles`). A user without a `profiles` row cannot log in even with the right password, because login resolves phone → email through that table.

Supabase Auth's own `phone` field is deliberately unused (it would require wiring an SMS provider). The number lives in `public.profiles` (`id` → `auth.users`, `phone` UNIQUE). Login returns **identical error text** for "no such number" and "wrong password" — splitting them would let anyone enumerate which numbers are registered. Tokens are never returned in a response body.

**Two roles, two panels (added 2026-09-11).** `profiles.user_type` is `'student' | 'teacher' | 'admin'`, defaulting to `student`. Schema and policies live in `supabase-teacher-panel.sql` (applied as three migrations; the file is their merged, idempotent form).

| host + path | who |
| --- | --- |
| `portal.akademitu.com/` | student dashboard — `PanelDispatch` sends teachers on to `/ogretmen` |
| `portal.akademitu.com/ogretmen` | teacher panel: weekly schedule + comments on completed lessons |
| `portal.akademitu.com/yorumlar` | student's per-lesson teacher comments |
| `portal.akademitu.com/yonetim` | admin panel: accounts, lesson assignment, fees |

The student panel **stays at the root**: most users are students and that address is already in bookmarks, in `PANEL_URL` and in `vercel.json`'s redirects. In `both` mode (localhost/preview) everything shifts under `/panel`. `src/lib/host.ts` owns all four path helpers; no component composes these paths itself.

**Reading the role from the DB on every request is the point, not an oversight** (`server/roles.ts`). `requireSession` resolves the session and loads `user_type` from `profiles` under the user's own JWT; `requireUserType(...)` then gates `/api/portal` (student) and `/api/teacher` (teacher). A Supabase custom JWT claim was considered and rejected: it needs an Auth Hook, and a role change would stay stale until the token refreshed. `requireSession` also calls `auth.getUser()` **once** and parks the result in `res.locals` — `portal.ts` used to call it itself, so this is the same number of round trips as before, not one more.

**Adding `user_type` opened a privilege-escalation hole that had to be closed in the same migration.** `profiles_update_own` previously pinned only `phone`, and `authenticated` has UPDATE on `profiles` — so any student could have run `update profiles set user_type='teacher'` on their own row and walked into a panel that shows other students' data. The policy now pins `user_type` as well; only `full_name` is user-editable.

**A policy with a subquery in its body breaks every `profiles` UPDATE — `42P17`.** `profiles_update_own`'s WITH CHECK subqueries `profiles`, which expands `profiles`' SELECT policies; when one of those (`profiles_select_as_teacher`) opened a subquery of its own, Postgres called it infinite recursion and **every** update failed, including a user renaming themselves. The fix is that `profiles_select_as_teacher` calls `private.ogrencim_mi(uuid)` instead of inlining an EXISTS. Keep policy bodies on `profiles` free of subqueries. The helper lives in a **`private` schema** because PostgREST publishes everything in `public` as RPC and the advisor flagged it (0029); revoking EXECUTE is not an option — the policy is evaluated as the calling user and needs it.

**`lessons` now has two SELECT policies, and they OR together** (`lessons_select_own` for the student, `lessons_select_as_teacher` for `teacher_id`). Every query that means "my lessons as a student" or "my lessons as a teacher" therefore carries an explicit `.eq(...)` — `portal.ts`'s long-standing "RLS already scopes this, a filter would be misleading" note is still true for `exam_results`/`payments`/`coach_notes` but **no longer for `lessons`**. Teachers see a student's name through `profiles_select_as_teacher`, which is scoped by *having a lesson with them*, not by role — one teacher account must not be able to enumerate the whole student roster.

**`lesson_comments` is one comment per lesson** (`lesson_id` UNIQUE), written by a single `INSERT ... ON CONFLICT (lesson_id) DO UPDATE`. Not DELETE+INSERT: two statements can interleave. It is **separate from `coach_notes`** and both are live — `coach_notes` is a general, dated note about the student and still renders on the dashboard; `lesson_comments` is tied to one lesson and renders at `/yorumlar`.

**The teacher marks the lesson taught — and that unblocked commenting entirely.** For a while nothing set `lessons.status`, and because `/api/teacher/lessons/:id/comment` rejects anything that is not `completed` with a 400, **no comment could be written at all**. `PATCH /api/teacher/lessons/:id/status` now moves a lesson between `scheduled` and `completed` from the teacher's own panel. Undo is allowed on purpose (clicking the wrong row is easy, and without it the teacher's only recourse is an admin); the comment row is **not** deleted on undo, it simply stops being visible to the student, whose list filters `status='completed'`.

**Letting a teacher write to `lessons` needs two separate restrictions, and neither alone is enough.** RLS says *which row*, never *which column* — with only a policy, a teacher could rewrite `subject`, `starts_at`, or `user_id` (moving the lesson to another student). So `authenticated` gets a **column-level** `GRANT UPDATE (status)` and nothing else; every other column returns 42501. The policy (`lessons_update_status_as_teacher`) then restricts rows to `teacher_id = auth.uid()` and values to `scheduled`/`completed` in **both** USING and WITH CHECK — USING keeps a `cancelled` lesson un-revivable, WITH CHECK stops the teacher setting one to `cancelled` (cancelling touches billing; it stays an admin decision). Both halves are measured in `supabase-teacher-panel-tests.sql`.

**Teachers cannot open lessons — only the admin panel can.** From 2026-09-24 to 2026-10-09 a teacher could open lessons for students they were already linked to (`POST /api/teacher/dersler`, `GET /api/teacher/ogrenciler`, `TeacherLessonForm`, the `lessons_insert_as_teacher` policy and a column-level `GRANT INSERT`). That was **removed on 2026-10-09**: the route, the endpoint backing its student dropdown and the form are gone, and `supabase-teacher-panel.sql` §5 now *revokes* the grant and drops the policy. Removing the code alone would not have been enough — with the policy still in place a teacher holding their own JWT could insert straight through PostgREST. §5 revokes at **table** level on purpose: in Postgres that also clears every column-level INSERT, and `authenticated` should have no INSERT on `lessons` at all (`GRANT UPDATE (status)` is a separate privilege and stays). Tests 28–32 in `supabase-teacher-panel-tests.sql` now all expect a rejection. A teacher's only writes are `status` and the lesson comment.

**`/api/teacher/schedule` is the teacher panel's only data endpoint.** It returns each lesson's status *and* its comment, so the week grid and the interactive lesson list below it read from one response; a separate `/api/teacher/completed` existed briefly and was removed because two surfaces editing the same comment drift apart. Marking or commenting patches that one lesson in local state rather than refetching the week — a refetch would wipe text being typed in another row.

**Week boundaries are computed at `+03:00`, not UTC** (`server/routes/teacher.ts`). "Which week" is a local question: in UTC a Monday 01:00 lesson lands in the previous week. Türkiye has been on permanent UTC+3 since 2016, so a fixed offset is correct and lives in one constant; the client mirrors it with an explicit `timeZone: 'Europe/Istanbul'` so a teacher abroad still sees Turkish times. An invalid or missing `week` falls back to the current week rather than erroring — it is a navigation parameter, not data.

**Teacher accounts are created by hand, like student ones** — there is still no signup. Same two steps as `supabase-portal-auth.sql` §1b plus `user_type = 'teacher'`; the procedure and the SQL for linking a lesson to a teacher are at the end of `supabase-teacher-panel.sql`.

**Accounts are no longer created by hand — the admin panel does it** (added 2026-09-11). `/api/admin/hesaplar` calls Supabase's **Admin API** (`auth.admin.createUser` with `email_confirm: true`) and then inserts the `profiles` row. Do **not** replace this with raw SQL against `auth.users`: the password must be bcrypted by Supabase and newer versions also need a matching `auth.identities` row, whose absence shows up as "the account exists but cannot log in". If the `profiles` insert fails the auth user is **deleted again** — a half-created account is worse than none, because its email then blocks a retry. The manual two-step in `supabase-portal-auth.sql` §1b still works and stays documented as the fallback.

The login email is **derived from the phone** (`<phone>@hesap.akademitu.com`) unless one is supplied. Login is by phone, so the email is internal plumbing; deriving it from a column that is already UNIQUE gets uniqueness for free.

**`/api/admin/*` uses `serviceClient()`, and that is deliberate — it is the exception the three-client rule did not anticipate.** `portal.ts` and `teacher.ts` avoid the service role so that a routing bug still cannot cross a user boundary. In the admin panel there is no boundary to cross: listing every student, assigning any lesson and setting any fee *is* the job, so RLS has nothing left to filter. Account creation needs the service role regardless. The consequence is that **the role gate is the entire boundary** — `requireSession` + `requireUserType("admin")`, with the role re-read from `profiles` on every request and unchangeable by the user (`profiles_update_own` pins it). Two things follow: every admin write is written to `audit_log`, since that is the only remaining record of what happened; and a missing `.eq("id", …)` in that file updates *every* row, because nothing downstream will catch it.

**The first admin was made by promoting the existing profile** (`update profiles set user_type='admin'`), not by touching `auth.users`. A chicken-and-egg otherwise: the panel that creates accounts is itself behind the admin role. Note the gate accepts exactly one role, so that account can no longer open the student panel — `/api/portal/*` returns 403 for it. An admin cannot demote themselves either; the route refuses it so the last admin cannot lock everyone out.

**When the admin assigns a teacher to a lesson, `teacher_name` is written alongside `teacher_id`.** The student panel renders that text column, and it is kept denormalised so a deleted teacher account does not erase who gave the lesson. The route also verifies that the selected people actually hold the roles claimed — `lessons.user_id` only references `auth.users`, so nothing in the database stops a teacher being filed as the student.

**Lessons are placed on the teacher's weekly availability, not typed in (added 2026-10-09).** A teacher account cannot be created without at least one availability range: `POST /api/admin/hesaplar` validates `availability` *before* creating the auth user, writes it after the `profiles` row, and rolls the whole account back (`deleteUser`, which cascades to `profiles`) if that write fails. Ranges live in `public.teacher_availability` (`supabase-teacher-availability.sql`): ISO weekday (1 = Monday), start/end as **minutes from midnight in Turkish time**, multiples of 30, end exclusive. It is RLS-on/no-policy/no-grant like `leads` — not a column on `profiles`, because `authenticated` has a table-wide UPDATE there and a teacher could have rewritten their own hours. Replacing a teacher's ranges goes through the `set_teacher_availability` RPC so the delete and insert are one transaction; the server merges overlapping/adjacent ranges first (`musaitlikNormalize` in `server/dersSaati.ts`). Existing teachers are edited from the "Müsaitlik" button in the accounts tab (`GET`/`PUT /api/admin/ogretmenler/:id/musaitlik`).

The lesson form has no date or end-time inputs any more. Picking a teacher opens their week (`GET /api/admin/ogretmenler/:id/program?week=`, same `weekUtils` week as the teacher panel) and a cell is clickable only if a lesson of the chosen length fits inside one availability range and overlaps none of the teacher's non-cancelled lessons. Length is derived, never sent: `lessons.is_trial` (the "Deneme dersi" checkbox) means 25 min, otherwise 50, and the server writes `ends_at`. `dersGovdesi` in `admin.ts` enforces all of it — teacher required, start on :00/:30, inside availability, no clash with the teacher's **or the student's** other lessons (409) — but **only when the slot changes** (new lesson, or start/teacher/trial changed, or a cancelled lesson reopened). Without that exception every lesson entered before these rules (14:15 starts, no teacher, no availability) could never be edited again, not even cancelled. Legacy lessons with no `ends_at` count as 50 min in clash checks. There is no DB exclusion constraint, so two admins booking the same slot at the same instant can both succeed; accepted for a single-admin panel. `src/lib/dersSaati.ts` mirrors the server's constants for the grid — keep 25/50/30 identical on both sides.

**Teacher descriptions are admin-only (added 2026-10-09).** Free text per teacher — subjects taught, notes — in `public.teacher_descriptions` (`supabase-teacher-descriptions.sql`): RLS-on/no-policy/no-grant like `teacher_availability`, and not a column on `profiles` for a sharper reason than availability's — a teacher can read their own `profiles` row in full, so a column there would be visible to them through PostgREST no matter what the UI hides. Written at account creation (optional; a failed write rolls the account back, same as availability) or via `PUT /api/admin/ogretmenler/:id/aciklama`, where empty text deletes the row. Read only through `/api/admin/ozet`, which **tolerates the table being missing** and returns the list without descriptions — so, unlike the availability migration, deploying ahead of this one cannot take the panel down. Audit logs `ADMIN_TEACHER_DESCRIPTION_WRITE` with the length, never the text. RLS tests 33–35 in `supabase-teacher-panel-tests.sql`.

**Teachers must accept a contract before the panel opens (added 2026-10-17).** A teacher who has not accepted sees a blocking modal (`TeacherContractModal.tsx`, gated inside `TeacherDashboardPage` so both the portal route and `both`-mode `/panel/ogretmen` are covered): the contract text, which must be scrolled to the end, then two **required** checkboxes — KVKK Aydınlatma Metni and Hizmet ve Kullanım Koşulları — then "Okudum, anladım". There is deliberately **no açık rıza**: under KVKK, consent that is a precondition for using the service is not freely given. Lessons are **not recorded**, which both texts state and the contract's 8.3 backs up. Yurt dışı aktarım rests on md. 9 standart sözleşme and is disclosed in the aydınlatma text. Starting to record lessons would need new versions of both texts. The gate is **server-side**: `server/routes/teacher.ts` mounts the contract router (`/api/teacher/sozlesme`) right after the role gate and `requireSignedContract` right after that, so every other teacher endpoint answers 403 `code: "SOZLESME_GEREKLI"` until accepted, while students and admins still get the *role* 403 first. The client reads that `code` from `ApiRequestError` and puts the modal back up. This happens from the schedule fetch and from `TeacherLessonList`'s status and comment writes alike, behind one loop guard (`sozlesmeyiYenidenSor`).

Schema is `supabase-teacher-contract.sql`. `teacher_legal_documents` holds all three texts, versioned (`kind` + `version`; the **current** document is the highest version — publishing a new one means inserting a row, not editing one). The owner pastes the contract itself; the aydınlatma and koşullar texts are seeded as v1 and are drafts for a lawyer to review. `teacher_contract_acceptances` is an evidence log storing the three document ids, both checkbox states, `accepted_at`, IP and user agent. It is append-only, and **enforced** by a trigger that rejects UPDATE, DELETE and TRUNCATE even for the service role and the Dashboard. A commented escape hatch in the SQL covers the rare legitimate deletion. A CHECK also rejects a body that still contains the template's "buraya yapıştırın": with no re-acceptance, a teacher who accepted the unfilled template would count as signed forever. "Is this teacher signed?" is answered from that log by the `teacher_contract_status` RPC (`yok` / `imzali` / `imzasiz`), one round trip per teacher request. **Until an `ogretmen_sozlesmesi` row exists the status is `yok` and the gate is inactive**, so the migration can go out before the contract text is ready. Three decisions are easy to undo by accident:
1. **No re-acceptance on a new version** (the owner's choice): one acceptance row means accepted forever. Switching to "re-sign on every new contract version" is a one-line change in the RPC. Because nobody re-signs, a document **cannot be edited or deleted once any acceptance references it** — a trigger in the `private` schema raises — otherwise editing v1 would silently rewrite what earlier signers agreed to. Fix typos before anyone signs; after that, insert version + 1.
2. **`teacher_id` is `ON DELETE RESTRICT`**: deleting a teacher who has accepted fails on purpose, since contract evidence should outlive the account (TBK md. 146, 10 years). Block (ban) the user instead. This includes the teacher `test:panels` creates on every run.
3. **`server/routes/teacherContract.ts` uses `serviceClient()`** — another documented exception to the three-client rule, for the audit_log reason: if the teacher could write the acceptance row with their own JWT, they could forge its IP, time and versions. Every query there is scoped by `res.locals.userId`; no teacher id is read from the client. The POST rejects ids that are not the current versions with 409 `SOZLESME_GUNCELLENDI`, so a teacher accepts exactly the text they were shown.

The gate fails **open only when the table or the RPC does not exist** (`nesneYokMu` in `server/semaHatasi.ts`), so deploying ahead of the migration cannot lock every teacher out. That check is deliberately narrower than `admin.ts`'s `EKSIK_SEMA_KODLARI`: a missing *column* means the schema drifted after the migration was applied, and it fails closed like every other DB error (503). Still run the SQL first. `/api/admin/ozet` adds `sozlesme: { onaylandi, tarih }` per teacher, shown as a badge in the accounts tab. It is `null` for everyone until a contract is published, or when either table can't be read, so the badge never claims "onay bekleniyor" while the gate is off. Audit logs `TEACHER_CONTRACT_ACCEPTED` with versions only. RLS tests 36–38; `test:panels` signs the contract for its own test teacher; that row, and therefore the account, cannot be cleaned up without the escape hatch. It skips the gate checks when no contract is published, and skips the remaining teacher checks when the teacher stays unsigned (an unsigned real `--teacher`, or a failing contract endpoint). The POST also answers 409 `SOZLESME_GUNCELLENDI` when no contract is published or the schema is missing: the modal refetches, gets `gerekli:false` and opens the panel.

**Form leads are readable in the admin panel (added 2026-10-04).** The "Başvurular" tab (`AdminLeads.tsx`) lists `public.leads` through `GET /api/admin/basvurular`: newest first, 50 per page, with search (the three name columns, plus the query's digits against `phone`) and exam/step filters, all applied server-side. Read-only on purpose — there is no edit or delete endpoint. The search term is embedded inside PostgREST's `or=(...)` syntax, where `,` `.` `(` `)` are separators, so `aramaMetni()` keeps only letters, digits and spaces; without it a crafted query rewrites the filter. Unlike the other admin reads, each listing writes `ADMIN_LEADS_VIEWED` to `audit_log` (page and row count, **never** the search text, which may be a phone number): this data belongs to people who have no account.

**CSRF and origin checks.** The `ALLOWED_ORIGINS` check in `server.ts` is **not** CSRF protection — it only inspects `Origin` when present and waves the request through when absent. Real protection is `requireTrustedOrigin` (`server/security.ts`), mounted on **both `/api/auth` and `/api/leads*`**: on state-changing methods `Origin` is **mandatory**, which is safe because browsers always send it on POST. A double-submit token was considered and rejected as redundant next to `sameSite=lax`. When `ALLOWED_ORIGINS` is unset it falls back to the request's own host, which is why production works without it — but set it anyway.

**Security headers live in `vercel.json`, not `server.ts`.** This trips people up: the middleware in `server.ts` only ever runs for `/api/*`, because the HTML pages are served straight from Vercel's static CDN and never touch Express. Until 2026-09-10 that meant every page — including the login screen with its password field — shipped with **no** `X-Frame-Options`, i.e. it could be framed for clickjacking. The `headers` block in `vercel.json` now covers all routes (`frame-ancestors 'none'` alongside `X-Frame-Options`), and adds `X-Robots-Tag` where it is needed — a server header, unlike `PageMeta`'s meta tag, does not depend on JS having run. Since 2026-09-10 that is `noindex, nofollow` for **every path on the portal host** (a `has: host` rule) plus `noindex, follow` on `/login`. `public/robots.txt` deliberately does **not** `Disallow` the portal: the same static file is served from both hosts, so a `Disallow: /` there would close the marketing site too — and blocking the crawl would also stop it from ever seeing the `noindex` header. Crawl, don't index. `Strict-Transport-Security` with `includeSubDomains` was added at the same time so the new subdomain is covered; `preload` is deliberately omitted (it is a near-irreversible commitment and nothing has been submitted to the preload list). Adding a header to `server.ts` alone will silently not apply to pages. Hashed build output under `/assets/*` gets `Cache-Control: public, max-age=31536000, immutable` from the same file (Vercel's default was `max-age=0`); never put an un-hashed file under `/assets/`.

**Lead form data flow (two-step, now server-mediated).** `src/components/PopUpForm.tsx` collects data in two steps. `src/lib/supabase.ts` still writes a `localStorage` backup (`derece_leads`) first as a fail-safe, then POSTs to `/api/leads` and `/api/leads/step2`. Step 2 calls the `update_lead_step2` RPC server-side, which targets that phone's newest `step = 1` row — do **not** replace it with `upsert(onConflict: "phone")`; `leads_phone_key` was dropped when repeat submissions were allowed, so that form fails with Postgres 42P10. Its `ORDER BY created_at DESC, id DESC` carries a **tiebreaker on purpose**: step 1 takes its timestamp from the server, so two submissions can share a millisecond, and `created_at` alone leaves which row gets updated undefined. Note also that a *repeated* step-2 call consumes the next-newest abandoned `step = 1` row for that phone, producing a second step-2 lead with identical data — a double-click can do it. Both routes now return real errors: they used to answer `success: true` even when the write failed (and when Supabase was unconfigured), which was invisible while the client talked to Supabase directly but would have meant silent data loss once the form went through them.

Anti-spam: honeypot (`website`), Turkish mobile format validated on the server, a mandatory `Origin` header, the global `enforce_leads_insert_rate_limit` trigger (20 inserts/minute site-wide), and a **Postgres-backed per-IP limiter** (`public.auth_attempts`, kind `lead`, 5 per 10 minutes).

**The limiter counts only attempts that did not succeed** (`success` false or NULL). It used to count every row for that IP, `success` ignored, so ten *correct* logins in fifteen minutes locked the account out — measured on production, where 9 of the 10 rows holding the IP at its limit were successful logins. Excluding them gives an attacker nothing: without the password every row they produce is a failure and still counts, so the 10-failures-per-15-minutes ceiling is unchanged. Do **not** "skip the limit when the password is correct" instead: the limit is evaluated *before* the password is checked, which is the whole point, so honouring it afterwards removes the cap on guesses entirely — and does so on the most privileged account. NULL counts as a failure, otherwise dropping the connection mid-request would be a free attempt. The per-IP counter used to be an in-memory `Map` in `server.ts`; that limited nothing on Vercel, where each serverless instance has its own memory and an attacker resets the counter simply by landing on a new one. No CAPTCHA; reintroducing Cloudflare Turnstile was considered and declined.

`auth_attempts` is pruned opportunistically (~2% of writes delete rows older than 24h) rather than by `pg_cron` — **pg_cron is not installed on this project**, so the cron block in `supabase-portal-auth.sql` silently no-ops and the table was never being cleaned.

**Audit log (`server/audit.ts`, `supabase-audit-log.sql`).** Separate from `auth_attempts` on purpose. `auth_attempts` is a **rate-limit counter** — keyed on IP + kind, queried as "how many rows in the last N minutes", pruned at 30 days, and it carries no `user_id`. `audit_log` answers a different question: *which user* logged in, logged out, or viewed their own data, from which IP and **from which host** (the last one only became answerable, and worth asking, once there were two hosts). Retention is 180 days via `public.prune_audit_log()`, called opportunistically at ~0.5% of writes — pg_cron is still not installed on this project, and the panel writes a row per dashboard load, so it needs a lower probability than `auth_attempts`' 2%.

**Failed logins are deliberately NOT written to `audit_log`** — `auth_attempts` already records every attempt with IP, phone and outcome. Duplicating them would mean an extra write per failure and two competing sources of truth for the same question.

Writes go through the **service role** and are fire-and-forget (`void`): a user must not be able to write to, and thus influence, their own audit trail, and a failure to log must never fail the request. Never put a password, token, cookie or payment detail in `detay` — the SQL file spells out why. Like `leads`/`auth_attempts`, the table is RLS-enabled with no policy and no grants, so the "RLS enabled, no policy" advisor warning is the intended state.

Testimonials are read through `/api/testimonials` (`TestimonialsSection.tsx` → `apiFetch`), same columns and ordering as before.

**Do not grant `anon` anything.** The whole point of `supabase-portal-auth.sql` is that `anon` ended up with no privileges at all; `supabase-anon-lead-insert.sql` is kept only as the documented way back if the proxy ever has to be abandoned. Supabase's security advisor reports "RLS enabled, no policy" for `leads`/`testimonials`/`auth_attempts` — that is the **intended** state here (no policy + no grant = nobody can reach them; only the service role, which bypasses RLS, touches them).

**Teacher photos load dynamically via Vite glob.** `src/utils/teacherLoader.ts` uses `import.meta.glob` to auto-discover images in `src/assets/teachers/*` or `public/teachers/*` at build time and turns filenames into display names; if none are found the ticker simply renders nothing (`DEFAULT_TEACHERS` in `src/config.ts` was deleted; the note below about it was stale). Adding/removing files in those folders changes the teacher carousel with no code changes needed.

**Routing and page structure.** `src/App.tsx` mounts **one of two route trees depending on the host** (see the two-host section above): on the portal host only the dashboard at `/`, everywhere else the marketing pages plus `/login`, the legal pages, the legacy `/portal*` redirects (`/portal/kayit` redirects to `/login` — it was briefly live before signup was removed) and a catch-all 404. The portal pages (login, student/teacher/admin panels, `PanelDispatch`) are `React.lazy` chunks so marketing visitors do not download them — this cut the main bundle from 544 kB to 451 kB on 2026-10-18; keep new panel pages lazy too. It also owns the global chrome (Header, Footer, floating call/WhatsApp buttons, sticky mobile CTA, cookie banner) and the popup form's open/close state, which is shared across the whole app rather than owned by individual pages. The portal screens deliberately render **without** that chrome (`isPortal` in `App.tsx`): the login screen is the product's front door, not a marketing page, and the sticky mobile CTA sat on top of its submit button. Note `isPortal` can no longer be derived from the path alone — the panel is at the *root* of its own host — so it checks the host first and only then `/login`, anything under `/panel` and the legacy `/portal*` paths. The `/panel` check is a **prefix**, not an equality: the teacher panel sits at `/panel/ogretmen` in `both` mode and an equality check left the sticky mobile CTA sitting on top of it. `App.tsx` also skips emitting the Organization/WebSite JSON-LD on the portal host: that host is entirely `noindex`, and publishing canonical site schema from it would contradict that. `AuthProvider` wraps the app in `src/main.tsx`. `src/pages/HomePage.tsx` composes the marketing sections (Hero, TrustBar, Packages, WhyUs, Subjects, Testimonials, FAQ — `SubjectsSection`'s subject list must match the FAQ's "Hangi derslerden özel ders alabilirim?" answer) and handles scroll-to-section navigation triggered via router `location.state`.

**Site-wide constants.** `src/config.ts` is now down to `SITE_URL` and `TEACHER_TICKER_PIXELS_PER_SECOND`; `BRAND_COLORS`, `CAMPAIGN_DEADLINE` and `DEFAULT_TEACHERS` were deliberately removed (the file says why). Brand colours live as literal hex in Tailwind classes — `#191F61` navy, `#B6D6CC` mint, `#c5a059` gold, `#101442`/`#1a1f5a`/`#2a3080` gradient stops — because there is no `tailwind.config`. The one theme token that does exist is `--font-sans` in `src/index.css`'s `@theme` block (Geologica); it must stay there rather than in `@layer base`, since Tailwind v4's utilities layer beats base and the `font-sans` utility on `<body>` would otherwise win — which is exactly why the site rendered in the system font until 2026-09-09.

## Environment variables

See `.env.example` for the full list. Key points:
- Anything prefixed `VITE_` is exposed to the browser bundle; secrets (`SUPABASE_SERVICE_ROLE_KEY`) must never carry that prefix.
- `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` **no longer exist.** The anon key moved server-side as `SUPABASE_ANON_KEY` (used for auth calls and for building per-user clients); `SUPABASE_SERVICE_ROLE_KEY` stays server-only as before. Nothing Supabase-related carries a `VITE_` prefix any more, and adding one back would undo the whole proxy layer.
- `ALLOWED_ORIGINS` is comma-separated and enforced server-side in `server.ts`. It now matters for every request, since all Supabase traffic goes through `/api/*`. **Leaving it unset is a valid and currently-live configuration** — `requireTrustedOrigin` then falls back to the request's own host, which is the right answer here because every host calls its own `/api`, and a foreign origin is still rejected with 403 (measured, not assumed). The dangerous state is *set but incomplete*: since the split it must list **all three** production origins — apex, `www` and `portal` — or the missing one 403s. So either leave it unset or list all three; never half of them. In dev this bites harder than in production, because Express also serves Vite's module scripts there, so a missing origin renders a blank page rather than just breaking the API. Include `http://localhost:3000` if you do set it locally. Note it is not CSRF protection on its own (see the CSRF note in Architecture).
- `COOKIE_DOMAIN` overrides the session cookie's `Domain`. **Leave it empty in production** — `server/cookies.ts` derives `.akademitu.com` from the request host and falls back to host-only cookies on localhost and preview deployments, which is what those environments need. Set it only to reproduce the two-host setup locally (e.g. `.akademitu.local`). A wrong value does not error; the browser silently drops the cookie and login appears to succeed while no session ever exists.
- `VITE_MAIN_ORIGIN` / `VITE_PORTAL_ORIGIN` override the two live addresses for local/preview work. They are hostnames, not secrets, so the `VITE_` prefix is fine here — this is not a hole in the "nothing Supabase-related carries `VITE_`" rule above. `vite.config.ts` reads the same two variables to build `server.allowedHosts`.
